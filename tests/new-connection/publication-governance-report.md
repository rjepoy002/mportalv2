Version/evidence tokens accepted by the registry are explicitly synthetic (`TEST-...`, `TEST-EVIDENCE-...`). Notice codes are the closed required set; languages currently supported by this test API are `en`/`fil`. These are foundation constraints, not official PALECO publication/language approvals.

Notice text is retained byte-for-byte; catalog/manifest JSON uses existing deterministic canonicalization. Database digest comparisons use binary comparison to avoid ASCII/UTF-8 collation ambiguity on the verified MariaDB engine. No browser-provided hash can override server-derived values. Matching hashes do not by themselves establish policy approval.

All version records, manifests, mappings, retirements, events and submission/publication links reject UPDATE and DELETE, including unpublished versions. Register another version instead of editing old content. The head alone is mutable under its guarded epoch protocol. Roles/permissions are not seeded by this migration; only a withdrawn empty head is initialized.

### Drift, interruption and rollback

The migration first verifies the earlier migration chain, then obtains its own advisory lock. Its checksum covers the new PHP/SQL artifact, and its signature covers all nine table definitions and `nc7_` triggers, excluding volatile AUTO_INCREMENT counters. Existing/unowned objects, incomplete `applying` ledger, changed checksums or schema/trigger drift fail closed. MariaDB DDL implicitly commits; this is not a claim of all-DDL transactional rollback.

`newConnectionGovernanceRollback(PDO)` requires a matching ready installation, zero rows in every governance evidence table, and unused epoch-zero head. It removes only the new tables/triggers and its ledger row, in FK-safe order. Populated rollback refuses. Reverse full dependency order is governance → submission receipts → draft receipts → foundation. The original rollbacks do not know about the new lineage FKs and must not run first.

Freeze writers and use the separately reviewed backup/restore procedure from [Task 06A](staging-readiness-report.md) before any future authorized deployment. Preserve populated history, notices, retirements and submission lineage; roll back code/disable routes and choose a reviewed restore/forward fix. Do not disable triggers, force FK deletion, edit a ready checksum or remove a schema guard. For an interrupted disposable test, discard only its exact validated random schema. No production migration adapter or backup/restore execution was introduced here.

## 3. Publication authority and internal API

`NewConnectionPublication(PDO $pdo, string $schema)` accepts only the established disposable-schema pattern and reuses strict/native PDO requirements. It loads no database/SMTP configuration and provisions no identities.

Every mutating operation locks/rechecks an active, email-verified actor and requires a current nonrevoked/nonexpired explicit staff assignment with:

- Permission code `publication.manage` through the existing module role-permission tables.
- Exact office scope `PUBLICATION`.
- Valid grant start/expiry metadata.

There is no publisher inference from email, Google, electric-service accounts, operational records or a general applicant profile. The tests alone provision a synthetic role/permission/assignment through their isolated administrator. Wrong scope, unrelated permission, missing/expired/revoked assignment, inactive and unverified identities are denied. Approval metadata records the explicitly authorized synthetic actor and evidence; **this is not a production two-person approval workflow or validation of legal authority**.

| Method | Contract |
| --- | --- |
| `registerNotice(actor, code, version, content, language, evidence): int` | Register immutable synthetic bytes/derived hash and server times; no hash/status override parameter. |
| `registerCatalog(actor, kind, version, document, evidence): int` | Register closed, bounded canonical synthetic document and derived hash, independently per kind. |
| `createBundle(actor, version, catalogIds, noticeVersions, evidence): int` | Assemble server-owned immutable manifest and FK mappings after relationship/compatibility/retirement checks. |
| `publish(actor, bundleId, expectedEpoch): int` | Verify active compatible components and expected epoch; publish/re-publish and advance epoch exactly once. |
| `withdraw(actor, expectedEpoch): int` | Withdraw head while retaining its last bundle and historical evidence; advance epoch. |
| `retireCatalog(actor, catalogId, expectedEpoch, evidence): int` | Append retirement and advance epoch. Retirement of a currently active component is denied until its bundle is withdrawn. |
| `historicalNotice(actor, code, version, hash): array` | Active verified caller retrieves exactly matching historical bytes/metadata, even after replacement/withdrawal. Wrong digest is denied. |
| `historicalCatalog(actor, id): array` | Active verified caller retrieves retained bytes/hash/version even after retirement. |
| `__invoke(): array` | Trusted provider: constructor bootstrap reads last retained bundle; inside the service transaction it locks the head and requires current published/nonretired effective components. |

Mutations own their transaction and reject nesting. No public command accepts arbitrary head state, applicant IDs for consent, publication flags or hashes. Expected epoch is optimistic conflict protection; stale publisher commands fail instead of silently applying another epoch. Internal actor arguments must come from authenticated server context in any future adapter. There is no HTTP publisher endpoint or staff screen.

Historical policy reads have active/verified identity checks; no production policy confidentiality/access scope beyond this synthetic foundation is assumed. All mutation audit rows contain fixed action/entity metadata and `{}`, not arbitrary content or applicant data. Detailed epoch history resides in the trigger-generated publication events.

## 4. Notice, catalog and contract versioning

Six catalog kinds are independently registered and retained:

1. **Localities:** bounded codes/names and province → city/municipality → barangay parent relationships, with explicit allowance for independent-city null province.
2. **Eligibility:** explicit boolean service-area eligibility for each locality in the selected bundle. Unknown/missing relationships fail bundle composition. Supply eligibility applies to proposed service location; residence outside a service area is not automatically rejected as a residence.
3. **Premises:** versioned code/label map.
4. **Occupancy:** independent versioned code/label map.
5. **Rules:** connection categories, allowed categories per premises, and occupancy codes requiring clarification. All references must exist in the selected classifications. Tests include synthetic studio/caretaker codes to prove rules are no longer hardwired to shop/other in governed contexts.
6. **Contract compatibility:** explicit applicant contract identifier, snapshot schema, workflow version and synthetic-only marker. The registry can retain other compatibility versions, but bundles using unsupported runtime versions are rejected.

Catalog documents use typed JSON with closed top-level fields, validated localities/relationships, bounded labels/codes and a 64 KiB canonical document cap. Cross-component relationships are validated when bundling, then checked again by the retained provider/contract at use. They are immutable version documents rather than a mutable lookup cache. The current runtime supports the existing draft contract/schema/workflow only; no “approved” production contract was invented.

The governed snapshot's `catalog_versions` retains all six independent version identifiers. Bundle manifests also bind component hashes/evidence, and review binding includes the full composed-catalog digest. New notice versions do not alter an existing bundle or its pending proof until publication changes. Reusing a registered notice/catalog version with different bytes conflicts; publishing the same bundle again still increments epoch and invalidates earlier pending proofs.

Retiring unused catalog versions preserves their bytes and advances the head epoch conservatively. A retired component cannot be placed in a new active bundle. Replacing active catalogs requires a valid replacement bundle; no operational `nc_arealist`, `nc_users`, membership/billing table or internet catalog is imported or used as fallback.

Original draft/service callers remain compatible with their existing synthetic context. A legacy mutable draft can be read and **explicitly saved** with governed metadata, incrementing the application version and requiring a new review. There is no silent bulk rewrite/backfill. Submitted snapshots remain immutable; their existing receipts are preserved. The retained documents plus the new submission/publication link explain the governed contract/catalog/notice context historically.

## 5. Submission transaction integration and lock order

Construct the governed service using the registry object directly:

```php
$registry = new NewConnectionPublication($fixturePdo, $disposableSchema);
$service = new NewConnectionStage1Submission(
    $fixturePdo, $disposableSchema, $registry, $serverKeyring
);
```

The service checks **exact PDO object and schema identity**, not merely equivalent DSNs. A separate-connection provider is rejected. Hiding the registry behind an untyped callback is also rejected. The older array callback remains only for existing synthetic regression fixtures; it is not a production provider/fallback and has no governed lineage claim.

The consistent resource order is:

- All commands first lock/revalidate their own user.
- Publisher commands lock their explicit assignment/permission rows, then the publication head. They never lock existing applicant applications while holding that head.
- Applicant commands follow the existing application → seven ordered stages → current revision → applicable receipt order, then take the publication head lock before validating/writing against new policy. New draft initialization has no existing application row to lock; after its user/head checks it inserts its new owned application.
- Immutable version rows are read only while the head protects publish/retire decisions. Foreign keys to actors refer to the already locked actor; publisher operations do not acquire applicant-user rows after the head.

This foundation deliberately uses an **exclusive `FOR UPDATE` head lock** for correctness. It remains held on the submission PDO until commit/rollback, including consent insertion, revision freeze, stage/event, lifecycle, publication lineage, audit and receipt. This serializes governed review/new-write policy resolution globally for `STAGE1`; production capacity/shared-lock alternatives require a separate measured design, not an untested optimization.

When submission acquires the head first, a withdrawal waits until its committed evidence exists. When withdrawal or replacement publication acquires it first, the submission sees the new withdrawn state/epoch and rejects without consent/evidence writes. Re-publishing unchanged bytes cannot resurrect a proof because the epoch changes.

Governed draft creation/new saves resolve policy inside their own transaction through the new protected validation-context seam. They deny new collection while withdrawn. Current authorized draft/history reads and exact already-committed retries are distinct; they do not create new data and need not pretend the old policy is still published.

The specialized submission path still performs complete canonical validation, server email/ownership/version checks, required acknowledgments, server notice hashes/times and the same single atomic commit. It does not call `NewConnectionWorkflow::transition()` afterward. A durable FK-backed bundle/epoch/key-ID association is added in that commit. No generic workflow or staff approval bypass was created.

Exact submission retry still rechecks current active/verified owner and record integrity before returning its original receipt. It returns before publication/proof revalidation, so withdrawal, proof expiry or removal of the former signing key does not re-execute or erase a committed outcome. New commands must use current policy and a valid proof. Different payload/key semantics and submitted revision immutability are unchanged.

## 6. Versioned review keys and proof protocol

`NewConnectionReviewKeys` owns no database access or storage. Inject key material from protected server memory; tests generate random synthetic keys and pass concurrency keys through the child process environment. No new private key bytes are embedded in source, table rows, logs, snapshots or receipts.

Version **2** proofs are canonical JSON/base64url plus HMAC-SHA-256. The authenticated envelope contains protocol version, key identifier (`kid`), issue/expiration times, nonce and server binding. The binding includes applicant identity, application/public reference/current revision, saved snapshot hash, application lock counter, contract version, independent catalog versions/full catalog digest, exact required notice versions/hashes, bundle ID/manifest digest and epoch.

Policy:

- Current signing key is required and cannot be revoked.
- At most three verification keys total: current plus at most two previous keys.
- Each nonrevoked previous key requires **fixed** `issued_through` and `verify_until` times. Verification overlap cannot exceed 300 seconds past that cutover; these times must not slide forward per request. Old keys cannot mint fresh acceptable proofs after their issuance cutoff.
- Unknown/revoked IDs fail closed; no key path/URL/database lookup is derived from a browser ID.
- Proof TTL remains 300 seconds. Default future-issuance skew tolerance is zero; an explicit server policy can allow at most 30 seconds. Expiration is never extended by that skew, and `now >= expires` is expired.
- Key withdrawal requires new review signed by an available current key. Keys are verified independently of identity/ownership/CSRF, not as authorization credentials.

Example server-only rotation configuration (key bytes omitted): current `k2`, bounded previous `k1` with its fixed cutover/verification window; or mark/remove `k1` for immediate rejection. New tests exercise both. Nonsecret key ID is retained in submission lineage; the raw proof remains only in command memory/digest, not in applicant snapshots.

Passing the earlier string-key constructor remains supported for existing synthetic tests and is wrapped as a single `fixture-default` key in the v2 protocol. Pending v1 proofs must be refreshed; this is not a silent acceptance of v1 as v2. Original v1 command receipts remain readable by the unchanged early authorized retry path without verifying the old proof again. No deployed live v1 submission service existed or was migrated here.

Real key provisioning, coordinated node rotation/revocation, clock synchronization and operator procedures remain deployment work. The injected keyring is a per-command trusted configuration snapshot, not a centrally managed production secrets service. Private keys must remain outside any future database publication registry and web root.
