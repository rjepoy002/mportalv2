## 2. Fixture environment and endpoints

The CLI harness connects to local MariaDB without selecting an actual portal database, creates a random `mco_nc_test_<16 hex>` schema, creates six synthetic users and applies the unchanged guarded Task 04/05C/05D migrations there. Users have BIGINT UNSIGNED IDs, `.invalid` emails and active/inactive/unverified cases. No linked-electric-account table exists in this schema; authenticated first-time applicants work without account linking.

The harness copies only the required services, helpers, prototype view/partials and local assets into a randomly named temporary document root. It does **not** copy actual database/mail configuration, business controllers or a production connection factory. Two independent PHP servers share the fixture database/session directory and listen on random loopback ports for concurrent HTTP tests. The adapter releases the PHP session lock before service database operations so session-file locking does not falsely serialize all requests.

The router runs only under `cli-server` with its generated private fixture configuration. Host headers must match the exact configured loopback endpoints; remote addresses must be loopback. There is no fallback for arbitrary PHP/static files. Direct requests for private configuration or CLI controls return 404. The source router returns 404 under the actual portal's normal web SAPI. The temporary copy of the test database support helper permits this controlled server SAPI; the original CLI-only support file is unchanged.

| Method and test-only path | Purpose / accepted command fields beyond CSRF |
| --- | --- |
| GET `/login` | Synthetic sign-in page; optional validated public reference `r` for explicit recovery. |
| POST `/api/login` | `login`, `password`; fixed synthetic login names map to server-owned test IDs. No portal credentials or client user IDs. |
| GET `/app` | Five-section editor using the existing PALECO shell; optional opaque `r`. Requires current active/verified session. |
| POST `/api/create` | `key`; calls existing transactional `create()`. |
| GET `/api/draft?reference=...` | Calls `retrieve()`; closed input plus current receipt/version tokens. |
| POST `/api/save` | `reference`, `expected`, `key`, `input`; calls `save()` with bounded contract input. |
| POST `/api/validate` | `input`, boolean `complete`; pure existing validator for section feedback, with authenticated server email/catalog. No writes. |
| POST `/api/review` | `reference`, `expected`; calls specialized `review()` for saved content/proof/published test notices. |
| POST `/api/submit` | `reference`, `expected`, `key`, `proof`, `selections`; calls only specialized atomic `submit()`. Exact retries return the original authorized outcome. |
| GET `/api/receipt?reference=...` | Calls `submissionReceipt()`; private current-revision outcome read. Never creates or replays a submission. |

POST command objects have exact per-endpoint key allowlists. Extra applicant IDs, workflow states, publication flags, notice hashes or staff permission fields are not accepted. GET draft/receipt query schemas allow only a well-formed public reference. No application content/proof/CSRF is placed in URLs; the address bar carries only an opaque public reference for reload/reauthentication recovery.

There is no HTTP endpoint for database migration, notice publication, clock control, user-status modification, staff actions, uploads, email, printing or operational queries. Negative-test publication/clock switches live in private harness files, written by the Node coordinator, not by browser commands. Synthetic user status changes use the CLI-only control. They induce failures; they do not bypass authentication, CSRF, proof verification or rate limits.

## 3. Authentication, CSRF and response security

The fixture uses `portalSessionStart()`, `portalAuthenticated()`, `portalAuthCsrf()` and `portalAuthCsrfValid()`. Successful synthetic sign-in regenerates the session and rotates pre-authentication state through the existing helper. A separate `NC_HTTP_FIXTURE` cookie/session directory prevents collisions with actual portal sessions. The same 30-minute idle/12-hour absolute helper policy applies.

Every private operation derives its actor exclusively from the session and re-reads that synthetic user's active/verified state. Persistence/review/submission services check current identity and ownership again inside their transactions. Known references, keys or review proofs do not authorize another applicant. Failed inactive/unverified fixture sign-ins use the same generic response, and changing a logged-in synthetic user's status invalidates subsequent access.

For POSTs, exact configured Origin is mandatory, JSON content type is mandatory, method must match and the existing CSRF token must validate. Cross-site/same-site Fetch Metadata is rejected; same-origin and user-initiated top-level navigation are allowed. GET responses also reject an explicitly foreign Origin or cross-origin Fetch Metadata. No permissive CORS headers are added. Unknown routes and unsupported methods fail closed; method failures carry Allow.

The raw request envelope is capped at 96 KiB before JSON processing; object/type/depth/field constraints then apply. Draft input retains the 64 KiB input / 32 KiB canonical contract limits; submission proof/selections retain their smaller service limits. The adapter never interprets browser fields as SQL identifiers, actor context or published policy.

Private HTML/JSON responses, including negative/error/rate-limit responses, use `Cache-Control: private, no-store`. The fixture adds nosniff and no-referrer. Its CSP restricts scripts/assets/connections to self; the existing inline theme bootstrap receives a per-response nonce. No unsafe-inline script exception or external CDN allowance was introduced, and production CSP/configuration was not changed.

Rate counters are locked server-side files keyed by **IP + fixed route + category**, outside PHP sessions. They cannot be reset by rotating cookies or logging into another test identity. Provisional fixture quotas per rolling window are:

- 60 GET/read requests per route per 60-second window.
- 200 general requests per route per window.
- After 12 invalid/denied requests per route/window, subsequent requests are rejected with 429.

The underlying 30-successful-draft/submission-writes/minute service budget is retained. HTTP 429 includes a Retry-After hint for the adapter limit. These are conservative fixture values, not approved production capacity policy. A deployment requires a shared multi-node limiter and load/lock-timeout acceptance; no production rate-limit store was added or weakened.

Infrastructure exceptions return a fixed generic 503 message; validation errors remain private field feedback. No raw exception/SQL/credential details are returned. The fixture has no application payload logger; PHP display/error logging is disabled for its server and stdout/stderr are discarded through the OS null device. Its limiter stores only route/IP digests, counts and times. Tests do not copy/log real credentials or applicant content. Existing service audits/receipts remain metadata-only under their prior allowlists.

## 4. Browser flow, review binding and recovery

The normal page retains Applicant Identity, Residential Address, Proposed Service Location, Service Request, and Review/Acknowledgments. Existing section navigation, Back/Continue, mobile normalization, copying, local icons, theme and focus/error summary code are reused. A new empty application can receive structured synthetic profile prefill; this is explicitly unsaved and still needs confirmation/save. No full-name splitting or actual profile update occurs.

Create obtains an opaque reference; Save Draft stores valid incomplete canonical data through the existing service. Resume reads the last committed draft rather than browser storage. Saved/unsaved states are distinct. A stale save produces a conflict dialog and requires explicit resume/review; resume warns before discarding unsaved changes. New edits during a save/review response are tracked by an edit generation so an older response cannot silently mark newer edits saved or install a stale proof.

Private review renders only the server-returned snapshot associated with its proof, not a fresh `read()` of unsaved form controls. The display includes identity/email, both complete addresses including postal codes, landmarks and selected synthetic service classifications/occupancy. Labels resolve against the fixture catalog supplied by the server. It does not present an official PALECO form. The candidate's confirmation flag differs from the stored draft flag as documented in Task 05D; substantive applicant content is exactly the reviewed saved content.

Review shows the provider's synthetic test notice versions/content and separate unchecked acknowledgment controls. Any applicant edit or Edit action invalidates the proof and selections; edited content requires another save and review. Expired proof, changed notice or withdrawn notice clears the current confirmations and requires fresh review. Production privacy/official-form approval is not inferred from these test notices.

Submission calls only `NewConnectionStage1Submission::submit()`. After success the editor/submit controls are hidden and the confirmation contains the public reference and explicitly states **Stage 1 in a disposable test database; not PALECO application approval**. No staff approval or installation status is displayed. Reload uses the private receipt read; it does not issue a submission POST.

The browser keeps proof, current versions and an uncertain submission command only in page memory. No applicant information is stored in localStorage/sessionStorage. Existing theme/sidebar preference keys are the only observed browser-storage entries.

For network interruption testing, CDP deliberately drops the first successful submission **response after the HTTP 200/commit was generated**. The interface reports an unknown result and offers an explicit Retry Exact Test Submission. That button resends the retained original command bytes/key/proof. The existing service returns its authorized durable result without additional consent/event/receipt rows. GET Receipt/Resume can also recover the outcome without posting again.

On expired session/CSRF, the interface clears pending command/proof/selections, disables editing/write actions and requests explicit synthetic reauthentication. Reauthentication loads only the last database draft; unsaved edits are absent. It never automatically replays a pending submission. The expiry test advances the server helper's fixture clock by 1801 seconds, exercising its actual idle-expiry branch without changing production helper settings; proof expiry is separately tested using the injected server proof clock. Rate-limit clocks/counters are not reset to make tests pass.

## 7. Remaining deployment and policy blockers

- The submission service still rejects `mco_portal`, and migration guards remain disposable-only. A separately reviewed production adapter/migration/backup/restore plan is required; this task does not authorize removing these guards or installing portal tables.
- Official locality/service classifications, requiredness/name exceptions, privacy wording, acknowledgment publication ownership, lawful real-draft collection, official forms and retention/hold/purge rules remain unapproved. Test publications are not PALECO legal approval or handwritten signatures.
- A production notice/catalog publication registry must coordinate versions/withdrawals transactionally across nodes. Fixture file switches test review invalidation but are not an administrative publication system.
- Production session/HTTPS/proxy configuration, CSRF integration with actual portal login, review-key provisioning/rotation, clock synchronization, shared rate-limit storage, safe monitoring/log redaction, database least privilege and sustained-load/deadlock behavior need deployment acceptance. The fixture's fixed synthetic password/login selector must never be deployed as authentication.
- Production UX still needs authoritative address data, reauthentication redirect validation, accessibility/physical-device and other-browser acceptance, retention messaging and approved notices before real collection. Review/content/command schemas must remain closed; private response/cache rules must extend to error middleware and reverse proxies.
- Existing portal feature preservation is supported by isolation and the listed regressions, not a claim that operational eBills/account/profile flows were exercised with live customer data. No live email or operational write was used for acceptance.
