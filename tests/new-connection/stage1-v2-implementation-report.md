## Implemented fields and behavior

1. **Applicant and Personal Information:** trusted synthetic structured profile is read-only; names are never split. Server profile fingerprint binds confirmation. A fixture action simulates a profile first-name change, clears confirmation/review and invalidates proof. DOB is required; age is calculated server-side from the fixture's reference date. Gender has exactly Male/Female/Prefer not to say. Civil status has exactly Single/Married/Widowed/Separated. Married requires spouse first/last; middle is non-required. Leaving Married clears spouse client-side and server-side.
2. **Additional Personal Information:** twelve approved education choices and non-required Other specification, occupation, income source, annual income, dependents, religion, social affiliation and TIN. All may be empty. Non-Other education clears specification. Sensitive input is denied when the trusted synthetic context disables it; corresponding inputs are not rendered. The supplied fixture permits fabricated examples only. This is not production collection authorization.
3. **Proposed Service Location:** server-owned Palawan context, TEST municipality/barangay identifiers, street, building, postal, directions and artificial test point/confirmation. No residential/same-address/premises/occupancy questions. Server validates hierarchy, coordinate range and selected fixture rectangle; it never claims actual Palawan eligibility. Coordinate edits/locality changes clear pin confirmation in the UI. Actual PSGC import, map centering, real geometry and tile provider are absent by design.
4. **Review and Confirmation:** escaped, server-canonical snapshot with expandable groups and explicit information confirmation. A private random server-session proof is bound to canonical content, profile fingerprint and reference date; changed content/profile or expiry rejects it. There is a proof-check action, **not submission**. The submission control is disabled and no submit route exists.

Required fields have red asterisks and `aria-required`; no Optional labels. Incomplete drafts are allowed. Validation errors are private, inline, and linked from a focusable error summary to the relevant section/control. Theme/sidebar/keyboard patterns reuse the existing shell. Unsaved changes warn on navigation; no applicant details enter browser storage.

The server clock fixture is fixed at **2026-10-22** for deterministic age tests, not browser-controlled. Age uses completed calendar birthdays, including March 1 for leap-day birthdays in non-leap years in this synthetic implementation. No minimum-age eligibility threshold is invented. Production date/age policy remains separately reviewable.

## Validation contract

Closed root sections: `personal`, `spouse`, `additional`, `service_location`, `confirmations`. Unknown fields/sections, identity/age/province/catalog/workflow overrides, incorrect JSON types, invalid UTF-8/control characters and overlarge input are rejected. Input cap 64 KiB; canonical snapshot cap 32 KiB; HTTP envelope cap 96 KiB.

Name limits remain 25 for applicable spouse fields. Extra text limits follow the consolidated proposed bounds. Annual income is a nonnegative decimal string (max ten integer digits/two decimals), canonicalized to two decimals; zero differs from blank. Dependents are an integer 0–999, not a boolean/fraction. Postal code is a four-digit string. TIN is limited safe digit/space/hyphen text and is not officially verified. Dates reject invalid calendar values, future dates and year zero. DOB/gender/status/spouse/location/pin/confirmations determine readiness separately from draft validity.

Profile identity and geometric versions come only from trusted fixture context. The browser's profile fingerprint is an expected-value token, not an identity payload; current server fingerprint must match before confirmation can be accepted. Geometry metadata in snapshots identifies artificial test boxes and explicitly says `synthetic_only_not_service_approval`. Submitted v1 history remains untouched; this phase creates no v2 submitted history.

## Session draft and proof scope

The fixture reuses current session start/authentication regeneration/CSRF helpers, with a separate synthetic cookie name and synthetic session initialization. It does not modify or call actual login, Google, Profile Settings or dashboard workflows.

Session save validates incomplete data, stores only the canonical input in the disposable server session and advances a session version. Expected-version mismatch conflicts. Random save keys bind to exact request content/version; exact retries return the original session receipt, changed payloads conflict. Receipts are bounded to 100 per session. PHP session locking serializes this demonstration; **this is not a database concurrency test or durable transaction service**.

Review validates the **current candidate**, not an immutable database revision. Completeness is simulated for generating the candidate review; the user must separately select review confirmation before proof-check. It cannot authorize submission because no submit endpoint exists. Proof lifetime is 300 seconds in manual mode and one second in automated test mode, controlled only by generated private configuration. Profile change or save removes the stored proof; content changes are also detected by fingerprint. No proof or personal values are logged.

Session expiry/closing the fixture removes this draft; durable recovery after reauthentication is not implemented. UI labels explicitly say session-only/no database. Existing v1 application-owner/database transaction/idempotency/immutable revision controls are not replaced. Session-only draft scope prevents cross-session retrieval and there are no browser-selected application/user IDs, but full v2 application ownership must be integrated with the existing services in a later disposable-schema task.

## HTTP and isolation

Only the copied fixture router runs under `cli-server` with its generated private configuration. It binds `127.0.0.1`, requires exact Host/Origin and same-origin Fetch Metadata, checks methods/JSON/body limits/CSRF and serves allowlisted static assets only. Private files and arbitrary PHP routes return 404. Errors are generic, private/no-store, and the fixture disables PHP payload/error logging. A shared locked counter limits fixture API requests; quota is not a production capacity policy. CSP serves local scripts/assets without adding unsafe-inline script/style allowances.

The temporary tree contains no actual database/mail configuration or operational controllers. The v2 fixture makes **no database connection**, so no schema/migration is needed for this phase. Regression suites that do require MariaDB retain their existing `mco_nc_test_<16 hex>` guards and cleanup. No actual customer identities or Google/SMTP requests are used. Real application/display/preview feature settings are not changed, and no actual portal route exposes v2.

## Manual review

From the project directory:

```powershell
& C:\xampp\php\php.exe tests/new-connection/stage1-v2-runner.php --start
```

Open the printed loopback `/login` URL, then select **Start synthetic profile session**. No real credentials. Use fabricated details only. Profile-change simulation is a fixture action, not Profile Settings. Select synthetic locality A/barangay A and an artificial point inside its displayed rectangle, then confirm. Review and proof-check; nothing can be submitted. Save/resume operate only in the temporary session. A new synthetic start resets that session demonstration.

Type `q` then Enter (or EOF) to stop and remove the temporary tree. Do not force-close the console: forced process termination/power loss cannot guarantee PHP cleanup. The runner leaves no persistent server after normal shutdown. It prints no real credentials, and no permanent route is installed. Existing v1 manual runner remains available independently.

Automated commands:
