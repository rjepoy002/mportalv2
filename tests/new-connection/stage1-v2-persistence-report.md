# Task 07B — Stage 1 v2 persistent synthetic drafts

2026-10-22. **Completed in disposable synthetic databases:** durable create/save/list/resume/abandon; profile refresh; version-safe retries; explicit v1→v2 revision conversion; committed-snapshot review; controlled session restart/expiry recovery. **No v2 submission endpoint, production migration or real applicant collection.**

## 1. Initial inspection and implementation decision

Before edits, reviewed the consolidated design, Task 07A report, v2 contract/dispatcher, v1 draft/submission/ownership code, schema/trigger guards, proof-key protocol and v2 fixture runner/router/UI. The inspection summary was provided before implementation.

Existing applications have opaque references, owner FK, creation key, lifecycle/lock/revision counters and seven stage rows. Revision `schema_version` already permits values ≥1; JSON snapshots carry executable contract identifiers and SHA-256. Current draft code hardcodes schema version 1 and v1 validation. Receipts are immutable records keyed per application/request; actor and current revision are locked inside service-owned transactions. Submitted revisions already have immutable-update/delete triggers. The existing proof-key service binds canonical metadata with expiry and HMAC.

Safe path: extend the existing service primitives through a disposable-only subclass, delegate v1 operations to the unchanged v1 service, and add conversion lineage plus source-freeze triggers. No existing table shape or original migration/checksum needs modification. Therefore no actual portal schema or production migration override was necessary.

## 3. Versioned service API

| Operation | Behavior |
|---|---|
| `createVersioned(actor, version, key)` | Explicit v1 dispatch to preserved v1 service or v2 creation; rejects unknown version. V2 stores schema version 2 and its executable contract string; seven stage rows initialize atomically. |
| `saveVersioned(actor, reference, version, expected, key, inputJson)` | Explicit version validation, current-user lock, owner checks, existing receipt replay, editability/expected token checks, current profile/context checks, pure contract validation, canonical snapshot/hash update, application lock increment, safe audit and receipt commit. |
| `retrieve(actor, reference)` | Owner-only editable v2 resume. Returns current saved receipt, canonical input, current trusted profile and changed-profile/geographic flags. No proof or accepted review confirmation is restored. V1 requires its preserved service or explicit conversion. |
| `listOwn(actor)` | SQL owner constraint and draft lifecycle filter; includes current revision/schema tokens for the closed fixture UI, at most 100 records. No cross-owner list. |
| `abandon(actor, reference, expected, key, confirmed)` | Explicit boolean confirmation; marks lifecycle `withdrawn`, advances lock, appends audit/receipt. No deletion of revision/history; exact authorized retry returns original result. |
| `convert(actor, reference, expected, key, confirmed)` | Explicit eligible v1 conversion to a new v2 revision; atomic lineage/source freezing and compatible-field mapping. |
| `profile(actor)` | Trusted current structured synthetic profile/fingerprint only; active/verified required. |
| `review(actor, reference, expected)` | Reads a committed editable v2 revision; validates current profile/context and completeness; returns the exact committed snapshot plus existing-protocol proof. Browser candidate data is not used. |
| `checkReview(actor, reference, expected, proof, confirmed)` | Separate explicit review confirmation; current owner/status/revision/profile/context/expiry validation. No submit operation follows. |

Inherited unversioned `create`/`save` entry points on this subclass fail closed; callers must use explicit version operations. The base v1 class remains unchanged. No draft is auto-converted, no v1 content is relabeled, and executable contracts remain `stage1.v1-draft-20261020` and `stage1.v2-synthetic-20261022`.

Receipt tokens are the existing exact typed set: application lock version, revision ID, revision number and snapshot SHA-256. Saves increment application lock/content version; draft revision number stays fixed until an explicit new revision such as conversion. Workflow version remains 1. Browser identity, role, schema, owner and server-derived metadata overrides are rejected by HTTP/contract validation; schema/context come only from generated private configuration.

## 4. Database and migration isolation

Every database test/run creates a new random `mco_nc_test_<16 lowercase hex>` schema. Workers share only their coordinator's assigned disposable schema. Bootstrap connects locally with **no selected database**, then a guarded connector validates the exact name before selecting it. The service rejects actual portal schema names and mismatched selected schema. The runtime test PDO additionally rejects operational identifiers, schema switching and cross-schema writes. No actual portal database/mail configuration or production credentials are loaded.

Synthetic `users` has BIGINT UNSIGNED IDs, structured names, contact, `.invalid` email, status and verification time. Two eligible owners plus inactive/unverified cases are seeded; no linked-account table is required. The fixture profile source is durable SQL, not a PHP-session identity snapshot or legacy full-name split.

Migration order for this fixture: existing foundation → existing draft receipts → **20261022 v2 drafts**. The original submission receipt migration is unchanged and remains exercised in separate v1 regression schemas. The new migration records readiness/checksum/signature and uses an advisory lock; reruns verify drift rather than replacing existing objects.

New table `new_connection_draft_conversions` records application, source/target revisions, actor and UTC timestamp, with restrictive FKs and unique source/target lineage. `nc7b_*` triggers make lineage immutable and freeze source revision updates/deletes after conversion. Existing `nc4_*` submitted-history and `nc5_*` receipt triggers remain intact. Original foundation/receipt signatures are unchanged because no original table or owned trigger is altered.

Schema version 2 is stored only in newly created disposable revisions; no production migration version or table was modified. Migration rollback succeeds only for a ready matching installation with no conversion or v2 records; populated history must be preserved. An interrupted applying migration requires investigation/recreation of the disposable schema, not automatic table replacement or a production guard bypass.

## 5. Transactions, locks, concurrency and recovery

Lock order follows the existing architecture: **current user/profile row → owned application → stages ordered by stage code → current revision → request receipt**, with creation/conversion inserts and dependent updates in the same transaction. Profile fixture updates lock the same user row. All SQL is parameterized for user/reference/content values; identifiers are trusted schema/table names. Native prepares, strict SQL mode and UTC are retained.

Prior receipts are checked before new-write version/editability checks, after current actor and ownership validation. This permits exact retries after later edits/abandonment without overwriting current data. Keys bind command kind, version and exact input/expected tokens; reuse with different content conflicts. Return values are the original safe technical receipt, not the latest applicant snapshot. A fresh resume is needed to see the newest data.

An inactive/unverified actor or another owner cannot recover a receipt. Submitted/withdrawn revisions cannot be newly saved. Audit metadata includes only application/revision counters; raw names/contact/address, proof and input payloads are not audit/error content. Invalid validation, stale tokens and injected failures commit neither partial snapshot nor audit/receipt changes.

Independent PHP workers/SQL connections tested competing saves (one winner), concurrent identical-key saves (one durable version change), save-versus-abandon (one winner), and a profile update holding the user lock while stale save waits then fails. This is actual database concurrency, unlike Task 07A's session serialization. There is no implicit deadlock retry/replay: on a deadlock/connection error the fixture returns a generic recoverable failure and the user must exact-retry or resume. Future higher-load/deadlock stress remains a deployment prerequisite.

Tests distinguish an **actual connection interruption** (KILL of the specifically attested disposable connection, followed by a fresh connection) from **simulated uncertain commit acknowledgment** (injected failure after successful commit). The latter is not claimed as a real network failure occurring at precisely commit time. Exact authorized retry with the same key recovers the original result, without duplicate version/audit changes.

## 6. Profile freshness, geography and committed review

Save/resume/review re-read and lock current SQL identity. Resume detects fingerprint mismatch, preserves other valid applicant input, returns current identity and clears profile/review confirmation in canonical input. It does not silently overwrite the committed identity snapshot. The applicant refreshes, confirms and saves explicitly. A stale-profile save is rejected; a committed old-profile review is unavailable until the refresh/save. This was tested with independent profile/save connections.

Changed catalog/geometry/eligibility context invalidates the review binding. Resume clears pin confirmation on version changes. A confirmed stale-context save is rejected: first save refreshed unconfirmed context, then explicitly reconfirm a compatible artificial point and save again. No live Palawan geometry, eligibility or map provider is introduced.

Review rebuilds the committed snapshot against current trusted context and checks its hash before issuing a proof. It uses `NewConnectionReviewKeys` with a private per-run random key and its existing 300-second protocol. Binding includes owner, contract, reference, application/revision/hash tokens, profile fingerprint, catalog/geometry/eligibility versions, reference date and privacy-context flag. Expiry/stale versions/profile/context fail closed. UI substantive edits clear the displayed proof and selection; no saved review authorization is automatically restored after resume/reauthentication.

The database snapshot has review confirmation false; the separate proof-check boolean represents review only. No actual v2 submission, consent publication, approval or receipt of payment is represented. Proofs remain private and are not stored in browser storage or audit payloads.

## 7. Explicit conversion

Conversion requires the authenticated owner, current editable v1 revision, exact expected versions, a fresh request key and explicit confirmation. Submitted, cross-owner, stale or downstream-processed sources are rejected. It creates revision number +1 with schema version 2 and the exact v2 contract identifier, rehydrates current SQL profile and preserves the original v1 bytes/hash.

Only existing **service** street/purok/sitio, building details, postal code and landmark are copied through explicit compatible mappings. No residential block, classification/occupancy, additional-address concatenation, editable v1 identity or `TEST-*` geography inference carries over. DOB/gender/civil status/spouse/education and coordinates remain missing; profile/review/pin confirmations reset. There are no v2 acknowledgments carried over from v1.

Current application and initial seven stage revision pointers advance transactionally; stage statuses/decisions are not invented. Source remains in its original draft state but is now immutable through lineage triggers; it is not falsely marked submitted. Conversion audits/receipts retain lineage, rollback removes all attempted new changes, and exact retry returns the same target revision. Existing submitted-history triggers are independently tested and unchanged.

## 9. Manual review and lifecycle

```powershell
& C:\xampp\php\php.exe tests/new-connection/stage1-v2-runner.php --start --persistent
```

Open the printed loopback URL; select **Owner A**, then start the synthetic session. Create a persistent synthetic draft. Save incomplete data, fill the four sections with fabricated information, save again, review committed information and check its proof. Select **End synthetic session**, sign in as Owner A again, choose **List my drafts** and resume. Owner B has a separate empty list and cannot access Owner A's reference. Inactive/unverified choices cannot authenticate.

One editable v1 sample is seeded for Owner A. Its list button explicitly asks to convert; canceling does not convert it. Abandonment also requires confirmation and retains historical records. Simulated profile changes are database-backed fixture updates, not actual Profile Settings.

Durability is within the disposable database's lifetime, across PHP sessions and connections. **Stopping/restarting the whole runner intentionally removes that database and creates a fresh one**; do not confuse cleanup with durable production retention. Type `q` then Enter or EOF to stop; servers terminate, nonfixture metadata signatures are checked, the exact generated schema is dropped and the validated temporary tree is removed. The printed schema/path support recovery if forced termination, machine crash or database outage prevents cleanup. Do not force-close the console. Verify the exact schema pattern and resolved system-temp `mco-v2-<16 hex>` child before manual cleanup; never drop/delete actual portal resources. No automatic broad stale-schema deletion is added.

The original `--start` / `--test` without `--persistent` still runs the Task 07A session-only compatibility fixture. This is not a second form or production workflow engine.
