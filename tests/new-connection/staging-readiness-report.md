### Privilege separation

- **Disposable test administrator:** may create/drop only the designated test databases and fixture DDL/triggers/data. The harness's broad local administrator access is not a runtime template.
- **Future staging migrator:** owner-approved CREATE/ALTER/INDEX/TRIGGER and required schema-specific DML/metadata/advisory-lock privileges. DROP is limited to reviewed empty-installation rollback/recovery; provisioning databases is a DBA operation, not an applicant endpoint. Verify trigger definer accounts/privileges survive restore and cannot gain unapproved operational access.
- **Module runtime:** SELECT necessary user identity fields; SELECT/INSERT/UPDATE only where the approved application/revision/stage operations require them; append-only INSERT/SELECT for evidence/audit/receipts; read-only role/catalog/publication access as needed. No DDL, no audit/consent/receipt UPDATE/DELETE, no ordinary runtime staff provisioning. - **Staff provisioning/publication/retention identities:** separate, explicitly authorized narrow capabilities with audit/approval; not inherited by applicant runtime.
- **Operational PALECO tables:** module receives no DML/DDL and preferably no connectivity unless a later approved read contract requires it. Existing portal's nine-column eBills INSERT exception does not grant New Connection permission. Preserve that existing functionality through its own approved integration/grants, not broader module credentials.

### Backup and restore verification

The DBA/process owner must approve RPO/RTO, maintenance window, encryption, access and retention; no values are invented here. Use a server-compatible logical/physical backup capturing relevant portal data, trigger definitions/definers and schema, with a protected credential option/configuration mechanism outside the web root. Never put passwords in commands or copy a sensitive dump into `tests/` or the deployment artifact. Freeze concurrent DDL; transactional table backup alone does not make DDL changes atomic.

Restore into a network-isolated nonmail environment, remap approved accounts/definers safely, and verify checksums/counts, FKs, exact canonical snapshot hashes, notices/consent lineage, append-only/submitted triggers, all three ledger signatures and authorized retrieval. Test the release with least-privilege runtime grants. Record restore duration and recovery evidence against approved RPO/RTO. A backup file existing is not a passed restore. No live backup/restore was performed for 06A.

### Drift, interrupted migration and rollback

Each migration uses an advisory lock, applying/ready checksum ledger and schema/trigger signature. An `applying` row, missing object, checksum mismatch or drift is a stop condition. MariaDB DDL implicitly commits: do not assume a transaction can roll back the whole migration. Different migration locks do not replace a maintenance writer freeze or global deployment coordination. Foundation/draft rollback should be reviewed for coordination before multi-operator staging use.

On interruption: keep writers/feature off, preserve an object/ledger inventory without row/secret disclosure, compare to the pinned manifest, and have the DBA choose verified restore or reviewed forward repair. Do not delete/reset ledger rows to force rerun or weaken the guard. Discarding the exact disposable schema is acceptable only for an authorized synthetic rehearsal; never use harness DROP DATABASE cleanup on the actual portal.

For **empty** installations, reverse dependency order is submission receipts → draft receipts → foundation. Receipts' owner/revision FKs otherwise prevent parent removal, and the original foundation rollback does not know about later tables. Each current rollback has its own emptiness/signature checks; foundation refuses any populated module data/catalog/history table. Once records/consents/receipts/history exist, prefer feature/code rollback while preserving tables/evidence, then reviewed restore/forward fix. Draft creation already generates history/receipts, so “no final submissions” does not mean safe to drop everything. Never disable append-only/submitted triggers or FK checks in an applicant request to undo a deployment.

## 6. Proposed publication and catalog design — not implemented

A production-safe model needs retained content, explicit publication authority and consistency through commit. Proposed future **portal-owned additive** structures/capabilities, subject to schema/policy approval:

- **Immutable notice versions:** code/version, exact canonical UTF-8 content or integrity-checked retained artifact, SHA-256 computed server-side, language, approval-evidence reference, approved/effective times and approver identity. Unique code/version; no replacing bytes under the same version. Keep the actual historical text accessible under policy, not merely a URL/hash. Do not equate publication with approval or approval with applicant consent.
- **Immutable catalog versions and entries:** separately version locality and service classifications/rules. Retain hierarchical locality codes/labels/service-area eligibility and explicit conditional service rules with provenance/approval/retirement history. Names/codes are strings, not assumed numeric IDs from `nc_arealist`. Submitted snapshots retain resolved labels and exact version IDs. No external live fetch or synthetic fallback during applicant rendering.
- **Publication bundles:** immutable reviewed manifest linking approved applicant contract/workflow versions, exact required notice versions/hashes, locality and service rule/catalog versions. Distinguish content approval from the bundle's current effective publication.
- **Locked publication head:** scope, active bundle reference, monotonically changing publication epoch and active/withdrawn state, with append-only publication/withdrawal events. Authorized publishers change this pointer/epoch rather than mutating historical content. Republishing identical content still changes the epoch; an old proof must not revive after withdrawal/republication.

Future table names such as `new_connection_notice_versions`, `new_connection_catalog_versions`, `new_connection_publication_bundles` and `new_connection_publication_heads` are **proposals**, not existing tables or authorization to migrate them. Required evidence associations, permissions and retention must be designed/reviewed first. Approval/publish/revoke authority is explicit staff capability, never an email-domain rule.

### Consistency protocol

For a new review/submission, use the **same database transaction/connection** to resolve and lock the publication head/bundle alongside current applicant/application/revision state. Use a target-engine-supported shared/exclusive locking protocol with a single documented lock order; publication mutations take the corresponding exclusive head lock and must not scan/lock applicant applications in the opposite order. Coordinate this with the current user → application → ordered stages → revision/receipt ordering; test deadlocks and contention before rollout.

Hold the publication lock until submission commit. If submission acquires a valid bundle first, its consent/content commit precedes a waiting withdrawal; if withdrawal commits first, the old proof's epoch/bundle fails before writes. A provider using a different PDO or reading a cached array cannot give that guarantee. Define the business meaning of already committed applications after withdrawal separately; do not rewrite/delete their evidence or silently reconsider them as new submissions.

Proof version must bind applicant/application/revision, lock counter, canonical content hash, contract version, independent catalog/rule versions and hashes, notice versions/hashes, **publication bundle/epoch**, purpose, key ID and expiry. Verify current eligibility again at submission. Preserve the existing false-to-true review-confirmation canonicalization rule deliberately or version it; never silently change stored submitted bytes/hashes.

Changing applicant content, required notices, service-area eligibility, rules, publication epoch or supported contract invalidates pending proofs. Withdrawn/unknown policy denies new draft collection/submission according to the approved scope; consent is required before whichever actual collection boundary privacy policy specifies. Existing authenticated receipt reads are distinct from permission for new collection and should preserve original outcomes while enforcing current owner/status access.

Drafts on older versions need an explicit migration/reconfirmation/assisted path that leaves submitted revisions immutable. Prevent process-global catalog caches from disagreeing with the proof/provider; the current prototype assigns the same catalog version to two domains and is not this independent-version implementation. Publishing and revoking concurrently, including unchanged-text republication, must be regression-tested with failure injection.
